# NEXAH Version 1.0 Ecosystem Editorial Guide

- Status: Release editorial guide
- Version: 1.0
- Review date: 24 July 2026
- Release gate at start: Gate 1 GREEN
- Authority: public positioning, editorial hierarchy and cross-link guidance
- Architecture change authority: none

This guide applies the canonical Public Release Claim, Release Roadmap,
Ecosystem Consistency Audit and Ecosystem Architecture & Narrative Review.

It does not redefine NEXAH, redistribute authority or reduce the scientific
record. It explains how each public surface introduces its own chapter of the
existing ecosystem.

> NEXAH is one ecosystem.
>
> Every repository, website and application is one chapter.
>
> Together they form one coherent Orientation Journey.

## 1. Ecosystem Story

### 1.1 The story in one paragraph

NEXAH is an orientation ecosystem for helping Humans work with questions,
sources, relationships, boundaries, uncertainty and provenance without
transferring meaning or judgment to software. Its research and Framework
preserve the intellectual and scientific development of this work. The
Orientation Language and Open Orientation Protocol define stable concepts and
participation boundaries. ORION provides the certified deterministic Core.
The Library, Atlas, books and papers preserve the public intellectual record.
NEXAHEDRON demonstrates one Human-facing implementation through a bounded
Orientation Session.

### 1.2 What every public surface must establish

Within the first screen or first 30 seconds, every surface must answer:

1. What is this?
2. Why does this particular surface exist?
3. What does it own?
4. What does it not own?
5. What is its current status?
6. Where should the visitor continue?

No surface should retell the entire history of NEXAH before answering those
questions.

### 1.3 What remains common

Every surface must preserve these shared statements:

- NEXAH is the complete ecosystem.
- Human judgment remains Human.
- Orientation is not recommendation, authorization or execution.
- Sources, versions, boundaries and provenance remain visible.
- Each subsystem has a bounded responsibility.
- Unknown, unsupported and uncertain states are not replaced with invented
  certainty.
- Version 1 proves one bounded and inspectable orientation process.

### 1.4 What may differ

Surfaces may differ in:

- audience;
- depth;
- terminology introduced after the first screen;
- editorial density;
- technical detail;
- interaction;
- visual emphasis;
- reading order;
- contribution route.

Consistency is achieved through compatible roles and transitions, not identical
copy.

## 2. Chapter Map

| Chapter | Public surface | Question it answers | Primary audience | Natural continuation |
|---|---|---|---|---|
| Discover | `nexah.de` | What is NEXAH, and where should I begin? | Everyone | Visitor Guide, Library, research, protocol or NEXAHEDRON |
| Understand | Position Paper, Public Release Claim, Visitor Guide | What problem does NEXAH address, and what does Version 1 prove? | Curious visitors, researchers, collaborators | Chosen Research, Build/Verify or Experience path |
| Read | Library, Atlas, books and papers | What has NEXAH published, and what sources or relationships can I inspect? | Readers, researchers, designers | Source, related work or NEXAHEDRON |
| Research | NEXAH Repository | What work led here, and how can it be inspected or reproduced? | Researchers and Framework developers | Research area, protocol, ORION or contribution route |
| Build and Verify | Orientation Language, RFCs and ORION | What is specified, certified and reproducible? | Implementers and reviewers | Proofs, reference implementation or contribution route |
| Experience | `nexahedron.com` and NEXAHEDRON | What does one Human Orientation Session feel like? | Participants and interaction reviewers | Orientation Record, source, `nexah.de` or protocol |
| Publish | NEXAH Experience Repository | How is the public intellectual home maintained? | Website maintainers and editorial designers | Live site or owning source |
| Apply | Declared Version 1 applications and cases | How does the existing orientation structure appear in a bounded context? | Domain users and application reviewers | Governing source or repository |
| Contribute | Repository-specific contribution paths | Where does this proposed change belong? | Contributors | Owning repository and governance process |

### 2.1 Public narrative

The ecosystem should not force one linear tour. The canonical movement is:

```text
Discover
↓
Understand
↓
Choose a path
├── Research
├── Build and Verify
└── Experience
↓
Apply within a declared boundary
↓
Contribute to the responsible surface
```

Research, Build/Verify and Experience are parallel paths. None is a prerequisite
for the others.

## 6. Cross-link Rules

### 6.1 One canonical home

Every artifact has one canonical home. Other surfaces provide only enough
context to explain why the link matters.

| Artifact or subject | Canonical home |
|---|---|
| Public identity and entry | `nexah.de` |
| Coordinated Version 1 state | Version 1 Release Manifest |
| Public release claim | Public Release Claim |
| Project problem and argument | Position Paper |
| Research and Framework lineage | NEXAH Repository |
| Orientation Language | NEXAH Repository language area |
| Protocol | Canonical RFC publication area |
| ORION certification | ORION Repository |
| Library identity and editorial provenance | Library registry |
| Public website implementation | NEXAH Experience Repository |
| Human reference session | `nexahedron.com` |
| Reference implementation source | NEXAHEDRON Repository |
| Orientation Record | Its originating NEXAHEDRON session or export |
| Governance | Canonical governance index |

### 6.2 Link labels

Use labels that describe the destination's role:

- “Read the Position Paper”
- “Inspect the certified ORION baseline”
- “Explore the Research & Framework Repository”
- “Begin an Orientation in NEXAHEDRON”
- “View the canonical Library record”
- “Read the Open Orientation Protocol”

Avoid:

- “Learn more”
- “Explore”
- “Enter”
- repository names without roles;
- unexplained acronyms;
- links whose destination changes responsibility without warning.

### 6.3 Status labels

Every cross-repository link to a component must expose its relevant status when
status affects interpretation:

- Certified;
- Version 1;
- Release Candidate;
- Alpha;
- Experimental;
- Historical;
- Proposed.

Component status and coordinated-release membership must remain separate.

### 6.4 Historical links

Historical material remains accessible and citable. Its entrance must state:

- historical period;
- whether it is current authority;
- the current canonical replacement or continuation;
- why the record remains preserved.

Historical material must never silently redirect in a way that destroys its
identity.

### 6.5 Outbound minimum

Every public surface must link to:

1. `nexah.de`;
2. the Version 1 Release Manifest;
3. its canonical owning documents;
4. its contribution route;
5. one appropriate next chapter.

The first-time journey must work without prior knowledge of ORION, JANUS, IEEE,
Kernel, Framework or RFCs.

```text
nexah.de
↓
What is NEXAH?
↓
What can Version 1 demonstrate?
↓
Visitor chooses:
├── Read one selected work
├── Understand the project
└── Begin an Orientation
↓
NEXAHEDRON reference session
↓
Orientation Record
↓
Return to source, Library or public explanation
```

### Editorial requirements

- Introduce “Orientation” before naming subsystems.
- Introduce NEXAH as the whole before naming repositories.
- Name NEXAHEDRON only when offering the Human experience.
- Name ORION only when explaining or verifying deterministic Core behavior.
- Introduce JANUS, IEEE, Human Field, Kernel and Framework inside the Research
  & Framework chapter.
- Introduce RFC numbers only after a visitor chooses the protocol path.
- Never require repository literacy to begin a session.

### First-session success

A first-time visitor succeeds when they can explain:

- NEXAH helps preserve orientation across material;
- sources and provenance remain visible;
- the Human remains responsible;
- NEXAHEDRON is where one session happens;
- ORION is a bounded certified Core, not an answer-giving agent;
- the Orientation Record is inspectable but not a final answer.

  NEXAHEDRON.
- Do not introduce future adapters, shared Memory or provider architecture into
  the Version 1 Builder path.

## 11. Editorial Style Rules

### 11.1 Lead with role

Begin every surface with:

```text
[Name] is [one role] within the NEXAH Orientation Ecosystem.
```

Do not begin with history, technology, features or an acronym.

### 11.2 Use one level of identity at a time

- NEXAH is the ecosystem.
- A repository is a repository.
- ORION is a certified Core.
- NEXAHEDRON is a reference implementation and Laboratory.
- `nexah.de` is the public and intellectual home.
- The Library is an editorial and provenance authority.

Do not call each of them “the platform,” “the system” or “the framework.”

### 11.3 Expand before abbreviating

On general public surfaces:

- explain the concept before using RFC numbers;
- explain the research area before using JANUS;
- explain the validation context before IEEE;
- name the owning implementation before “Kernel”;
- qualify “Framework” as the NEXAH Framework.

Specialist surfaces may use established terms after their first definition.

### 11.4 Separate status dimensions

Write:

> ORION Version 1 is certified and is one component of the coordinated NEXAH
> Version 1 release.

Do not write:

> The entire ecosystem is certified.

Write:

> This experiment remains active research.

Do not let “experimental” silently describe the whole ecosystem.

### 11.5 Preserve authority in verbs

Use:

- the Human selects, relates, reflects, confirms, rests and decides;
- the Library identifies, versions and preserves provenance;
- the protocol defines;
- ORION constructs, validates and certifies its bounded artifacts;
- NEXAHEDRON presents and preserves the Human session;
- `nexah.de` explains and routes;
- research investigates and tests.

Avoid verbs that transfer authority:

- NEXAH knows;
- ORION understands meaning;
- NEXAHEDRON decides;
- the Library proves;
- the website validates;
- an Orientation Record answers.

### 11.6 Preserve limits

Every capability statement should name its boundary when omission could create
a false expectation.

Prefer:

> The session preserves the fragments the Human selected.

Over:

> The session identifies the important evidence.

### 11.7 Keep technical history below current guidance

## 13. Final Release Readiness Assessment

### Assessment

The ecosystem has a coherent editorial model. It does not require a new name,
new architecture, reduced research scope or uniform copy.

The release is not editorially ready until the canonical model is visible at
every public entrance.

### ✓ Release Blocker

1. Publish the authoritative Version 1 Release Manifest and reading order.
2. Position the public NEXAH repository explicitly as Research & Framework
   within the complete ecosystem.
3. Reconcile the ORION first screen with the certified Version 1 baseline.
4. Publish a reachable and inspectable NEXAHEDRON Version 1 reference
   implementation.
5. Route “Begin an Orientation” from `nexah.de` to the verified NEXAHEDRON
   session rather than to the older ORION journey.
6. Publish the canonical Position Paper, Public Release Claim, RFCs and
   governance path.
7. Reconcile component maturity with coordinated Version 1 release membership.

### ✓ Important Before Release

1. Apply this guide's role, non-role and transition block to every repository
   front door.
2. Make the Visitor Guide the public role-based routing layer.
3. Align GitHub profile descriptions and canonical repository ordering.
4. Label current, historical, experimental and proposed material consistently.
5. Add canonical edition and status orientation to the Library, Atlas, books
   and research territories.
6. Ensure every public link names the role of its destination.

### ✓ Version 2

1. Additional application front doors.
2. Broad adapter or provider participation.
3. Shared Memory, collaboration, synchronization and cross-session identity.

These items must not enter the Version 1 editorial path.

### Release condition

The ecosystem is editorially ready when an unauthenticated first-time visitor
can:

1. begin at `nexah.de`;
2. understand NEXAH without knowing internal names;
3. distinguish research, protocol, Core and reference implementation;
4. choose a path without reading repository architecture;
5. complete the bounded NEXAHEDRON session;
6. inspect its Orientation Record;
7. locate the source and public claims;
8. identify the responsible repository for any deeper question.

At that point the scientific depth remains intact, but no visitor is required
to understand the whole ecosystem before entering the chapter relevant to
them.
